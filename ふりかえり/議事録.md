# ふりかえり議事録(Bacon)

## KPT出た意見
### Keep
  - 最終的にはカリキュラムに追いついて課題を提出することができた。
  - ブランチの使い方や、コンフリクトやマージミスへの対処法が分かってきた。
  - 早く終わった人が次の工程に必要なExcelなど土台の準備をしてくれたことで、スムーズに進められた。
  - 手が空いた人から次の工程に進む
  - 手が空いた人が進んでいない仕事を引き受ける
  - 最初にひな型を作成する
  - 目標をやや高めに設定したことでのモチベーションの持続
  - 設計段階でgitで競合することなくスムーズに進められた
  - 作業分担が適切に行われていた場面が多く、常に作業に取り組む時間を確保できていた。
  - 実装が難しかったところは周りにも頼って意見や考えを求めることで解決していけていた。
  - 暇な人に仕事を割り振りと待たず進められたのはよかったと思う
  - どこまでやるかをメンターに頻繁に確認できていたこと
  - Gitでトラブルもあったが、それもあり復元などのやり方を学べた。
  - 遅れていた進捗を巻き返していった。
### Problem
  - 誰が何をしているのか全員が把握できておらず、無駄が生まれる可能性があった
  - PMが機能していなかった
  - 終わっていないのに発表前日でもいつも通り焦らず仕事を進めてしまっていた
  - 要件定義で全体感を想定できていなかった
  - メンターと教員の指示ずれのため、全員の意思が統一されていなかった
  - メンターさんからの合格をいただけず、修正に時間を要していた。（結合テストシナリオ）
  - プログラミングでの機能実装に時間をかけてしまった。（ログイン機能・カテゴリー検索）
  - メンターさんとの認識合わせが行えていない部分があった。（作業の進め方や課題の取り組み方）
  - 提出形式が違う
  - 進捗報告がない
  - 担当範囲がわからない
  - PMがいないことで提出する人を毎回決める手間があった
  - 期限遅れがあった
  - 残業しまくった
  - developでうまくマージできないことがあった
  - メンターに中間報告しなかった結果、修正箇所があとに響く形になった
  - フロントエンドのバリデーションが作れなかった
  - 十分に理解できていないままプログラムした結果、テストで苦労した
  - カテゴリや検索を設定したメソッドを使用せず実装していた
  - スマートフォンに適したデザインにできなかった
  - スコープの修正が数回あった
  - 進捗状況が把握できない
  - 属人的になってしまっている
    - 重い範囲を一人で行うなど
    - 完成度のゴールが人によって違う
  - 期限内に終わらない
    - 一人ひとりの進捗がよくない
    - 問題が解決しない
  - 意思疎通があまり取れていなかった
  - やることについての理解度があまりよくなかった
  - 詳細設計段階から遅れが出てしまい、要件定義の段階から機能を削った。
  - 機能への理解が俗人的になってしまったことで作業量にも差が生まれた。
  - カテゴリ機能の実装に想像以上に時間を要してしまった。
  - 大幅な進捗の遅れがあり、皆がやっていることがばらばらで自分のPMの時に進捗管理がまともにできていなかった。
### Try
  - オンラインの日にも進捗報告を行い、どこが遅れているかを把握できるようにし、進めなければならないという意識を芽生えさせる。
  - こまめにメンターの方に質問をし、大きな手戻りや無駄な作業が発生しないようにする。また、質問をする際にこちらの状況や意図が正しく伝わるように工夫する。
  - 管理者ツールの実装
  - 大文字小文字のバリデーションをフロントに実装
  - PMを一人明確に決める
  - プログラミン段階でスコープ外にしたことをやりたい
  - フロントエンドのバリデーションを実装したい
  - 課題内容の整合性が取れていなかったことや網羅性の不足が原因だったと考えるので、提出前の確認と、提出前にメンターさんに中間的な確認を取るべきであった。
  - 最終的に実装ができているため、その点ではよかったと感じる。進捗の見積もりが甘かったと考えるので、事前作成に加えて、随時調整・変更を加えることで遅れが極力でないよう努める。
  - 自分たちの中だけで決めたり納得したりせずに、共有・確認を徹底して（可能なら毎日）いくことで認識がズレないようにしていく。
  - 全員のタスクとその予定のリストを作る
  - どの作業がどのくらい大変かを学んだので、最適な時間配分を行うのと、そもそもの機能に取り込むか適切な判断をする
  - 複数のメンター（関係者）からどうすべきかをもっと確認する
  - メンターの方など、詳しい人にもっと積極的に質問し、効率を高める。
  - 共通のドキュメントやチャットなどに各自の進捗報告を行い、進捗管理を行いやすくする。
  
## グルーピング
### Keep
- チーム連携・作業分担
   - 作業分担が適切に行われていた
   -  手が空いた人から次の工程に進む／未完了の作業を引き受ける
   - 実装が難しかったところは周囲に相談して解決できた
   - 暇な人に仕事を割り振りと待たず進められた
   - 早く終わった人が土台を整備しスムーズに進んだ
  
- Git活用・トラブル対応
   - ブランチやマージ、コンフリクト対応がわかってきた
   - 設計段階で競合なくスムーズに進んだ
   - Gitのトラブルから復元方法を学べた

-  目標・モチベーション管理
   - 高めの目標設定でモチベーション維持
   - 最終的に課題提出に追いついた／進捗を巻き返せた

### Problem
- 進捗管理・共有不足
  - 誰が何をしているのか把握できていない
  - 進捗報告がなく状況が不透明
  - 属人的な対応（重い作業の集中、進捗に差）
  - 進捗状況が見えず、PMとして管理できなかった
  - 提出担当が毎回決まっていなかった

- PM・リーダー不在／機能していない
  - PMが不在または機能していない
  - 意思統一ができておらず、指示にずれ

- 遅延・納期未達
  - 大幅な進捗遅れ
  - 期限遅れ／一人ひとりの進捗が悪い
  - 詳細設計から遅れ始め、機能を削った
  - 残業が増えた

- 設計・仕様認識の甘さ
  - 要件定義の段階で全体像がつかめていなかった
  - 機能の理解が俗人的／設計と実装の乖離
  - カテゴリや検索のメソッドを無視した実装
  - フロントバリデーション未実装／スマホ対応不備
  - そもそもの理解不足／AI質問も的確にできなかった

- メンターとのコミュニケーション
  - メンターとの認識ずれ
  - 中間報告を怠ったため、修正が後に響いた
  - 課題提出形式の認識違い
  - 結合テストでメンターの合格が得られなかった

### Try
- 進捗管理・共有強化
  - オンライン日にも進捗報告し、意識付けを行う
  - 全員のタスクと予定をリスト化する
  - 共通のドキュメントやチャットで進捗共有する

- PMの明確化／リーダーシップ強化
  - 明確にPMを一人決める
  - 自分たちだけで判断せず共有・確認を徹底（毎日が理想）
  
- 設計・計画の見直しと精度向上
  - 機能に対する労力と時間配分の見積もり精度向上
  - スコープの適正判断／スコープ外の取り込み検討
  - 課題整合性や網羅性の確認を提出前に徹底

- メンター連携強化
  - メンターにこまめに質問して手戻りを防ぐ
  - 状況や意図を伝えて効果的な質問を心がける
  - 複数の関係者から意見を得る

- 技術的チャレンジ
  - 管理者ツールの実装
  - フロントエンドのバリデーション実装（大文字小文字含む）


## 深堀り
進捗管理
【チーム内での報連相不足】
- チーム内での完成度・形式に対する認識が一致していなかった、共有できていなかった
→作業を始める前に完成図や形式の認識を一致させる話し合いをしたうえで、全員が知識を十分に蓄積した状態でタスクを振り分けられればよかった
- 誰がどこをどれだけやっているのかわからない
  - ドキュメント等で(情報を可視化して)進捗を共有していなかった 
    →Teamsで都度連絡
      - 事前準備不足
        →指針を予め決める
【メンターとのコミュニケーション不足】
- 認識のずれによる手戻りが発生した(スコープの修正等)
→メンターをある程度コントロールする必要があった
- レビュー待ちの時間が多くあり、進められなかった
  - 他にやることがわからなかった
  - 中間報告をしておらず、一回のレビューに対する負担が大きくなってしまった	
    →中間報告をすればよかった
  - 進捗等の計画をこちらから提案できなかった
- 前段階でOKが出たものに関して、以降の工程でNGが出ることがあった
→鵜呑みにするのではなく、チーム内でOK項目を再確認すべきだった
- 計画段階で、どれくらい時間がかかるか分かっていなかった
【遅れへの対策不足】
- 進捗が遅れてしまったにもかかわらず、対策を講じなかった
→リカバリーの際のスケジューリング
→納期を守るという意識を強く持つ

## 改善策（Try）
- Teamsで進捗を都度報告
- 作業を始める前に完成図や形式の認識を一致させる話し合いを設ける
- 指針を予め決める
- 全員が知識を十分に蓄積した状態でタスクを振り分ける
- メンターをある程度コントロールする
- 納期を守るという意識を強く持つ
- リカバリーの際のスケジューリング
- 鵜呑みにするのではなく、チーム内でOK項目を再確認する
- 中間報告をする
- 作業を始める前に完成図や形式の認識を一致させる話し合いが必要だった

### アクションプラン
- 作業前に「完成イメージ」と「提出形式」の認識合わせを行う
内容：作業開始前に、完成図・提出形式をチーム全体で共有・確認するミーティングを実施する
担当：PM主導、全メンバー
時期：各フェーズの作業開始前


-  進捗の「見える化」を実施する（Teamsで都度報告）
内容：日々の進捗をTeamsの共有チャネルに投稿し、タスクと状況を全員が確認できるようにする。ガントチャートやWBSを活用する。
担当：全メンバー
時期：毎日（朝・夕）

- 中間レビュー・報告をスケジュールに組み込む
内容：スケジュールに中間レビューの日時を事前設定し、メンターとの認識ずれや手戻りを防ぐ
担当：PM
時期：各工程の折返し時点

- タスクを割り振る時には「必要知識の確認」と「事前キャッチアップ時間」を設ける
内容：アサイン前に担当者の理解度を確認し、必要であれば事前学習の時間を設ける
担当：PM
時期：各タスク割り振りが決まった段階

- 想定外の遅れへの「リカバリープラン策定」を事前に行う
内容：各マイルストーンで遅延時の対処方法（人員再配分・優先順位変更など）をあらかじめ定義しておく
担当：PM
時期：プロジェクト計画時点（初回キックオフ時）
