# 機能：注文機能

## テスト対象API

- `POST /api/orders` （このテストケースでは `/api/orders/confirm` を使用）

## テストデータ準備方針：

- テストの独立性を保つため、各テストケース実行前にデータベースをクリーンな状態にし、テストケースごとに必要な商品データを投入することを想定します。
- 以下では、テストデータとして投入される商品情報を `Product(ID, Name, Price, Desc, Stock, ImageUrl, IsRecommended)` の形式で記述します。

## テストシナリオ

### No. 3-21

- テストケース名: 注文（異常系 - (模擬) 在庫更新時にエラー発生）
- 前提条件:
    - DBにテスト商品として以下の商品が登録されていること:
        - `Product(1, "木製コースター（4枚セット）", 1800, "天然木を使用したシンプルなデザインのコースター。4枚セット。", 50, "/images/wooden-coaster.png", false)`
        - **注: 注文数を多くすることで在庫更新が起きるように想定**
    - セッションに以下のカート情報が存在すること:
        - `Cart(items={"1": CartItem(productId=1, quantity=3, subtotal=5400)})`
    - フロントエンドのフォームは適切に記入されており、バリデーションを通過する状態であること。
    - **(テスト実装上の工夫)**: `ProductRepository.decreaseStock(1, 3)` が呼び出された際に、`0` を返す（更新失敗）か、または例外をスローするようにモックまたはテスト用実装で設定する。

- 手順:
    1. フロントエンドで注文フォームに顧客情報と決済方法を入力する。
        - **入力例**: 名前: "顧客 太郎", メール: "test-member-a@example.com", 住所: "東京都品川区", 電話番号: "0123456789", 決済方法: "銀行振込"
    2. 「注文内容を確認する」ボタン（`#submit-order-form-and-show-confirmation`）をクリックする。
    3. フロントエンドで顧客情報と決済方法のバリデーションが成功し、`currentOrderData` に情報が格納される。
    4. カート情報の取得API (`GET /cart`) が呼び出され、カート内容が `currentOrderData.items` に格納される。
    5. 注文確認モーダルが表示される。
    6. 「注文を確定する」ボタン（`#final-confirm-order-btn`）をクリックする。
    7. HTTP POSTリクエストを `/api/orders/confirm` エンドポイントに送信する。
        - **HTTPリクエスト**: `POST /api/orders/confirm`
        - **リクエストボディ**: `currentOrderData` の内容
        - **セッション**: 上記前提条件のカート情報
    8. -> OrderController
    9. OrderControllerがCartService.getCartFromSession(session)を呼び出し、カート情報を取得する。
    10. OrderControllerがOrderService.placeOrder(カート情報, 注文リクエスト)を呼び出す。
    11. OrderServiceがカート内の商品の在庫確認を行い、問題ないことを確認する。
    12. OrderServiceが注文情報を構築し、OrderRepository.saveを呼び出し、DBに注文を保存する。
    13. OrderServiceがProductRepository.decreaseStock(1, 3)を呼び出す。
    14. -> ProductRepository (意図的に失敗する/例外をスローするように設定されている)
    15. ProductRepository.decreaseStockが更新失敗を示す戻り値（例: `0`）を返す、または例外をスローする。
    16. OrderServiceが更新失敗を検知し、`IllegalStateException`をスローする。
    17. OrderControllerのtry-catchブロックで`IllegalStateException`を捕捉し、エラーレスポンスを生成する。
    18. HTTPレスポンスを受信する。
    19. フロントエンドでエラーメッセージを表示する（`handleError`関数経由でアラートなど）。

- 入力データ (APIリクエストとして送信されるデータ):
    ```json
    {
      "customerInfo": {
        "name": "顧客 太郎",
        "email": "test-member-a@example.com",
        "address": "東京都品川区",
        "phoneNumber": "0123456789"
      },
      "paymentMethod": "銀行振込",
      "items": [
        {
          "productId": 1,
          "name": "木製コースター（4枚セット）",
          "price": 1800,
          "quantity": 3,
          "subtotal": 5400
        }
      ],
      "totalPrice": 5400,
      "shippingFee": 0, // 仮定
      "grandTotal": 5400 // 仮定
    }
    ```

- 期待結果:
    1. HTTPステータスコードが **`409 Conflict`** であること（`OrderService` 内で `IllegalStateException` がスローされ、`OrderController` の`catch (IllegalStateException e)`ブロックで処理されるため）。
    2. レスポンスボディがJSON形式であり、エラーメッセージ **`"商品 木製コースター（4枚セット） の在庫更新に失敗しました。時間をおいて再度お試しください。"`** を含む `OrderResponse` であること。
    3. DB状態変化: `orders`, `order_details`, `products` テーブルに変化がないこと（`@Transactional` によりロールバックされる）。
    4. セッション状態変化: セッションの `cart` 属性がクリアされずに残っていること。
    5. `OrderService.placeOrder` 内で `productRepository.decreaseStock` が呼び出され、その戻り値が `1` でないため `IllegalStateException` がスローされること。`OrderRepository.save` は呼び出されるが、その後の在庫更新失敗によりトランザクションがロールバックされるため、DBには永続化されないこと。`CartService.clearCart` は呼び出されないこと。
    6. **フロントエンドの挙動:**
        * 注文確認モーダルが閉じられ、エラーメッセージのアラートが表示されること（`handleError`関数経由）。
        * カートの内容はクリアされず、注文フォームもリセットされないこと。
